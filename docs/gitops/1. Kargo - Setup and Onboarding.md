# 1. Kargo: Setup and Onboarding

How Kargo promotes **packaged Helm charts and container images** through environments, and how to put a new application on that path. The process is generic; the DIGIT 3.0 core module (Kargo project `digit-core3-0`) is the worked example throughout.

## 1.1 The idea in one minute

A release of a service is **two artifacts that belong together**:

| Artifact | Where it is published | Example |
|---|---|---|
| Container image (and its `-db` migration image, if any) | Docker registry | `egovio/mdms-v2:master-8ea5702` |
| Packaged Helm chart | Helm repository | `mdms-v2` chart `3.0.0` from `https://helm.digit.org/digit3/core` |

Kargo pins one image tag and one chart version together as **Freight**, and moves that Freight from environment to environment. A promotion **writes the pinned versions into the environment's values file in git**. Argo CD notices the commit and deploys exactly those versions.

```
 Docker registry ─┐                                   git: env branch
                  ├─► Warehouse ─► Freight ─► Stage ─► environments/<env file>.yaml
 Helm repository ─┘   (discovers)  (pins)   (promote)    <service>.chart-version: 3.0.0
                                                          <service>.image.tag:     master-8ea5702
                                                                │
                                                                ▼
                                                     Argo CD deploys that chart
                                                     version with that image tag
```

Nothing deploys unless a person promotes it. Kargo never talks to the application's cluster to deploy; **git is the hand-off**.

## 1.2 Vocabulary

| Term | Meaning here |
|---|---|
| **Project** | One Kargo project per module (a group of services released together), for example `digit-core3-0`. It is a Kubernetes namespace on the Kargo control-plane cluster. |
| **Warehouse** | One per service. Watches the service's image repository and chart, and turns what it finds into Freight. |
| **Subscription** | What a Warehouse watches: an `image` (registry repo + tag filter), a `chart` (Helm repo + chart name) and, optionally, a `git` path. |
| **Freight** | An immutable bundle: one image tag + one chart version for one service. What you promote. |
| **Stage** | One per service per environment, named `<service>-<env>` (for example `mdms-v2-dev`). Holds the Freight that environment runs. |
| **Promotion** | Moving a piece of Freight into a Stage. Runs the Stage's steps: clone the env branch, write the versions, commit, push. |
| **Env file** | The environment's values file in git (for example `environments/unified-digit3-core-dev.yaml`). Kargo writes into it; Argo CD reads it. |

## 1.3 How the setup is deployed

Everything Kargo-related is itself deployed by Argo CD from git:

| Part | What it is | Where it lives |
|---|---|---|
| Control plane | Kargo API, controller, webhooks, UI | `deploy-as-code/helm/charts/kargo/config/control-plane.yaml`, installed by `argo-cd/<env>/kargo/kargo-application.yaml` |
| Pipeline chart | A Helm chart that renders a Project's Warehouses, Stages, promotion policies and RBAC from one values file | [`deploy-as-code/helm/charts/kargo`](../../deploy-as-code/helm/charts/kargo) |
| Project config | One file per project: its services, stages, tag rules and teams | [`deploy-as-code/helm/charts/kargo/config/projects/<project>.yaml`](../../deploy-as-code/helm/charts/kargo/config/projects) |
| Pipelines ApplicationSet | One Argo CD Application `kargo-<project>` per project; renders the pipeline chart with that project's config | [`argo-cd/unified-dev/kargo/kargo-app-set-pipelines.yaml`](../../deploy-as-code/helm/charts/argo-cd/unified-dev/kargo/kargo-app-set-pipelines.yaml) |
| Credentials | Registry, git and SSO credentials, SOPS-encrypted, rendered by cluster-configs | see [Kargo Setup 2.5](../kargo/2.%20Setup.md) |

So **you never create Kargo objects by hand**. You edit the project config in git, raise a PR, and Argo CD renders the Warehouses and Stages.

One control plane (on the dev cluster) drives every environment: promotions to qa and uat are just commits to the qa and uat branches, which those clusters' own Argo CD instances deploy.

## 1.4 Warehouses: where builds are discovered

A Warehouse is created for each entry under `services:` in the project config. It has up to three subscriptions:

| Subscription | Added when | What it discovers |
|---|---|---|
| **image** | always, unless the service sets `image: false` | Tags of `<registry>/<repo or name>` that match the tag filter |
| **chart** | the service sets `chart:` | Versions of that chart in `chartRepo` (service-level, else project-level) |
| **git** | the service sets `configPath:` | Commits touching that path (used by the older git-path chart model) |

### Tag filters decide what can ever be released

Registries hold many tags: mainline builds, feature-branch builds, per-architecture children. The filter is a regular expression, and only matching tags become candidates.

| Setting | Level | Effect |
|---|---|---|
| `allowTags` | project (default for all services) or service (replaces the default) | The main filter |
| `extraAllowTags` | service | Added to the filter with `\|` for one service's extra build families |

Anchor every pattern on the trailing commit hash so the per-architecture children (`-amd64`, `-arm64`) never match:

```yaml
kargo:
  # mainline and flyway-branch builds; "[0-9a-f]{7,}$" keeps -amd64/-arm64 tags out
  allowTags: '^(master|flyway-branch)-.*[0-9a-f]{7,}$'
  services:
    - name: keycloak
      chart: keycloak
      # this service only has keycloak-spi-custom-build-* builds
      extraAllowTags: '^keycloak-spi-custom-build-.*[0-9a-f]{7,}$'
```

A Warehouse that finds nothing shows **Not Ready: "No references discovered"**. The filter matches no tag in the registry; fix the filter, not the Warehouse.

### Chart-only services

Some charts ship no image of their own, for example a module's ConfigMaps/Secrets chart, or a third-party chart whose image is fixed by the chart. Set `image: false`: the Warehouse subscribes to the chart only, and Freight carries only the chart version.

### Discovery settings

| Setting | Recommended | Why |
|---|---|---|
| `freightCreationPolicy: Manual` | yes | Freight is assembled by a person, so nothing appears in a Stage unexpectedly |
| `interval: 5m0s` | yes | How often the registry and Helm repo are re-scanned |
| `cacheByTag: true` | yes | Repeat scans are cheap |
| `discoveryLimit: 20` | yes | How many matching tags/versions are offered (newest first) |
| `imageSelectionStrategy: NewestBuild` | default | Orders tags by image build date |

## 1.5 Freight: the thing you promote

With `freightCreationPolicy: Manual`, you **assemble Freight in the Kargo UI**: open the service's Warehouse, choose one image tag and one chart version, and create the Freight. From then on that combination is fixed.

Rules of thumb:

- **Choose the tag deliberately.** `NewestBuild` orders by the image's build date. Some images report the same build date for every tag, so the list order can be meaningless. Pick the tag you intend, not the first one shown.
- **The app image and its migration image share the tag.** For services with `dbMigration: true`, the promotion writes the same tag to the service image and to `<service>-db`. Both images must exist for that tag.
- **The chart version must exist in the Helm repository for as long as any environment uses it.** If a published version is deleted, Argo CD can no longer render the app (it keeps the last cached render only until its cache is refreshed).
- **Freight is per service.** Releasing five services means five Freight.

## 1.6 Stages and promotion

For every service and every stage in the project config, the chart renders a Stage `<service>-<stage>`.

### The promotion path

```yaml
  stages:
    - name: dev                     # takes Freight straight from the Warehouse
      branch: unified-dev
      envFile: deploy-as-code/helm/environments/unified-digit3-core-dev.yaml
      autoPromotion: false
    - name: qa
      from: dev                     # takes only Freight that has been in dev
      branch: unified-qa
      envFile: deploy-as-code/helm/environments/unified-digit3-core-qa.yaml
      autoPromotion: false
    - name: uat
      from: qa
      branch: unified-uat
      envFile: deploy-as-code/helm/environments/unified-digit3-core-uat.yaml
      autoPromotion: false
```

- **dev** accepts Freight from the Warehouse; **qa** accepts only Freight that has been in dev; **uat** only Freight that has been in qa. Promotion is linear.
- `autoPromotion: false` everywhere: every promotion is a person's click.
- **uat accepts `master-*` builds only** (`masterOnlyStages`, default `[uat]`). Any other tag makes the promotion fail loudly before anything is written. There are no per-service exemptions.

### What a promotion does

1. Clones the stage's `branch`.
2. Writes the Freight's versions into the stage's `envFile`.
3. Commits `kargo: promote <service> to <stage>` and pushes to the branch.
4. Optionally (`argocdUpdate: true` on the stage) asks Argo CD on the same cluster to sync the app immediately. Packaged-chart projects do not need this: Argo CD picks up the commit within about a minute.

### The keys it writes

Under the service's section (`valuesKey`, default the service name):

| Key | Value | Written when |
|---|---|---|
| `<service>.chart-version` | chart version from the Freight | the service has `chart:` |
| `<service>.image.tag` | image tag from the Freight | the service has an image |
| `<service>.initContainers.dbMigration.image.tag` | the same image tag | `dbMigration: true` |

Example commit to `unified-digit3-core-dev.yaml`:

```yaml
mdms-v2:
  # ...hand-written values stay as they are...
  chart-version: '3.0.0'
  image:
    tag: 'master-8ea5702'
  initContainers:
    dbMigration:
      image:
        tag: 'master-8ea5702'
```

### Merge vs update

| `envFileWrite` | How keys are written | Seeding needed |
|---|---|---|
| `merge` (use for new projects) | Generated document merged into the env file; **creates missing keys** | No |
| `update` (default, older projects) | Replaces existing keys only | Yes: every key must already exist, or the promotion fails with "key path not found" |

The promoted keys are **owned by Kargo**. Every other key in the env file is written by people through PRs (see the SOP).

## 1.7 Onboard a new application

To add a service to an existing project:

**Prerequisites**

- [ ] The chart is **published** in the project's Helm repository (or `chartRepo` for this service).
- [ ] At least one image tag that matches the project's `allowTags` exists (or plan an `extraAllowTags`).
- [ ] If the service has a migration image, `<service>-db` exists with the same tags.
- [ ] The values the service needs (replicas, ingress, env overrides) are known. They go in the env file by PR.

**Steps**

1. **Add the service to the project config**, `charts/kargo/config/projects/<project>.yaml`:

   ```yaml
       - name: my-service
         chart: my-service              # chart name in the Helm repo
         dbMigration: true              # only if it has a <name>-db image
         freightCreationPolicy: Manual
         imageSelectionStrategy: NewestBuild
         cacheByTag: true
         discoveryLimit: 20
         interval: 5m0s
         # extraAllowTags: '^my-branch-.*[0-9a-f]{7,}$'   # only if needed
         # deploy:                                        # only if not the project default
         #   layout: root                                 #   (see the Argo CD doc, 2.5)
         #   namespace: other-namespace                   #   must be in kargo.argocd.namespaces
   ```

2. **Add hand-written values to the env file(s)**, if the chart's defaults are not enough: a `my-service:` section with replicas, ingress and so on. **Do not** add `chart-version` or image tags; Kargo writes those.
3. **Raise one PR** with both changes. After merge, Argo CD renders the new Warehouse and Stages (`kargo-<project>` app).
4. **Check the Warehouse is Ready** and shows image tags and chart versions.
5. **Create Freight** (image tag + chart version) and **promote to dev**.
6. **Verify in Argo CD**: with Kargo-managed Applications, the app `<prefix><service>` appears within about a minute of the promotion commit. Check it syncs and becomes Healthy.

Promote to qa and uat later, in order, the same way.

## 1.8 Onboard a new project

Use a new project when a group of services is released on its own cadence, or needs its own values file, namespace or access list.

1. **Project config**: create `charts/kargo/config/projects/<project>.yaml` (copy `digit-core3-0.yaml` as the template). Set:
   - `project`: the name. Lower case, digits and dashes; no dots (it becomes a namespace).
   - `registry`, `chartRepo`, `allowTags`, `envFileWrite: merge`.
   - `argocdAppPrefix`: unique across all projects; Argo CD app names are `<prefix><service>`.
   - `stages`: dev → qa → uat with each env file and branch.
   - `teams`: who may view, promote and assemble Freight (see [Role Based Promotion Access](../kargo/4.%20Role%20Based%20Promotion%20Access.md)).
   - `argocd`: only if Argo CD should create the apps from this config (see the Argo CD doc, 2.4).
2. **Pipelines ApplicationSet**: add `- name: <project>` with its `branch` to `argo-cd/unified-dev/kargo/kargo-app-set-pipelines.yaml`.
3. **Env files**: create one per stage, `environments/<prefix>-<module>-<env>.yaml`, holding the module's `global` values and hand-written per-service values. Use a separate file per module, so its keys never collide with another module's.
4. **Credentials**: make sure the project namespace receives the registry and git credentials (cluster-configs `secrets.kargo.projects`).
5. **Argo CD side**: AppProject, config/secrets app, namespace (see the Argo CD doc, 2.8).
6. **Raise the PR**, then check that `kargo-<project>` syncs and every Warehouse becomes Ready (or is Not Ready only because no matching builds exist yet).

## 1.9 Field reference

### Project level (`kargo:`)

| Field | Meaning |
|---|---|
| `project` | Project name (= namespace). |
| `registry` | Image registry prefix, for example `docker.io/egovio`. |
| `chartRepo` | Default Helm repository for `chart:` services. |
| `chartVersionKey` | Env-file key for the chart version (default `chart-version`). |
| `allowTags` | Default tag filter for all services. |
| `masterOnlyStages` | Stages that accept only `master-*` images (default `[uat]`). |
| `envFileWrite` | `merge` or `update` (see 1.6). |
| `argocdAppPrefix` | Prefix of the Argo CD Application names. |
| `git.repoURL` | Repository holding the env files. |
| `stages` | The promotion path (below). |
| `teams` | Access (see the existing access doc). |
| `argocd` | Optional: project-level deploy settings read by the Kargo-managed ApplicationSets (`project`, `namespace`, `namespaces`, `layout`). |

### Service level (`services[]`)

| Field | Meaning |
|---|---|
| `name` | Service name: Warehouse name, Stage prefix, default env-file section. |
| `chart` | Chart name in the Helm repository. |
| `chartRepo`, `chartSemver` | Per-service overrides of the project values. |
| `image` | `false` for a chart-only service. |
| `repo` | Image repository name if different from `name`. |
| `valuesKey` | Env-file section the keys are written under (default `name`). |
| `dbMigration` | Also write the tag to `initContainers.dbMigration.image.tag`. |
| `allowTags` / `extraAllowTags` | Replace / extend the tag filter. |
| `freightCreationPolicy`, `interval`, `cacheByTag`, `discoveryLimit`, `imageSelectionStrategy` | Discovery behaviour (see 1.4). |
| `deploy` | Optional Argo CD placement: `layout`, `namespace`, `app`, `releaseName` (see the Argo CD doc). |

### Stage level (`stages[]`)

| Field | Meaning |
|---|---|
| `name` | Environment name; Stages are `<service>-<name>`. |
| `from` | Upstream stage; omit on the first stage. |
| `direct` | With `from`, also accept Freight straight from the Warehouse. |
| `branch` | Git branch the promotion commits to. |
| `envFile` | Values file the promotion writes. |
| `autoPromotion` | Keep `false`. |
| `argocdUpdate`, `argocdNamespace` | Ask the same-cluster Argo CD to sync right after the push. |
| `color` | Colour in the Kargo UI. |
| `verifyKubeconfigSecret` | Enables post-promotion verification for that stage (needs `verify.enabled`). |

## 1.10 Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Warehouse Not Ready: "No references discovered" | No image tag matches the filter (or the chart is not published) | Check the registry tags and the regex; add `extraAllowTags` for the service by PR |
| Freight offers the wrong "newest" tag | Images report identical build dates | Pick the tag explicitly when assembling Freight |
| uat promotion fails: "REJECTED: only master-* images…" | Non-mainline image | Promote a `master-*` build; there are no exemptions |
| Promotion fails: "key path not found" | Project uses `envFileWrite: update` and the key is not seeded | Seed the key by PR, or move the project to `merge` |
| Promotion succeeded but nothing deployed | The Argo CD side is missing: no Application for the service | See the Argo CD doc: Kargo-managed config or ApplicationSet element |
| Deployed app pulls the wrong image tag | The chart ignores `image.tag` in its default mode | Set the chart's override switch in the env file (DIGIT 3.0 common chart: `global.mode: dev`) |
| Migration init container fails on checksum or "already exists" after changing builds | App and migration builds mixed, or migrations writing into a shared schema | See the SOP, 3.7 |
