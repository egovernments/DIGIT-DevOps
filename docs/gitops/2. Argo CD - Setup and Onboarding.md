# 2. Argo CD: Setup and Onboarding

How Argo CD deploys applications from git, how a chart version travels from an env file into a running Deployment, and how to onboard a new application or module. It works **with Kargo** (Kargo writes the versions) or **on its own** (people write the versions by PR). The DIGIT 3.0 core module on unified-dev is the worked example.

Read this together with [1. Kargo: Setup and Onboarding](1.%20Kargo%20-%20Setup%20and%20Onboarding.md) and [3. SOP and Guardrails](3.%20SOP%20and%20Guardrails.md). The older model, where charts are taken from git paths, is described in [Deploying Services in Unified Environments](../argocd/Deploying%20Services%20in%20Unified%20Environments.md).

## 2.1 The model

- **Git is the only source of truth.** Every cluster object that Argo CD manages is rendered from this repository; changes are made by PR.
- **One branch per environment.** `unified-dev`, `unified-qa` and `unified-uat` each describe one cluster. A change reaches an environment only by landing on its branch: by PR, or by a Kargo promotion commit.
- **Packaged charts.** Applications install a **versioned chart from a Helm repository** (for example `https://helm.digit.org/digit3/core`). The version to install is a value in the env file, not a git path.
- **Env file.** One values file per module per environment (`environments/<prefix>-<module>-<env>.yaml`) holds the global settings, each service's values, and the chart version and image tag to run.

```
                         env branch (git)
  environments/<module>-<env>.yaml          charts/argo-cd/<env>/...
  ├─ global: …                              ├─ AppProjects
  ├─ <service>:                             └─ ApplicationSets
  │    chart-version: 3.0.0  ◄── Kargo                │
  │    image.tag: master-…   ◄── Kargo                │ read the env file
  │    replicas, ingress…    ◄── PR                   ▼
  └─ cluster-configs: …                  Application <prefix><service>
                                          chart <service> @ chart-version
                                          values from the env file
                                                      │
                                                      ▼
                                      Deployment / Service / Ingress in the namespace
```

## 2.2 Layout in git

| Path | Contents |
|---|---|
| `deploy-as-code/helm/charts/argo-cd/bootstrap/<env>-bootstrap.yaml` | The one Application applied by hand per cluster. It syncs everything below. |
| `deploy-as-code/helm/charts/argo-cd/<env>/<area>/` | One folder per area (`egov`, `health`, `digit3-core`, `kargo-managed`, …): its AppProject, ApplicationSets and Applications |
| `deploy-as-code/helm/environments/` | Env files and their SOPS-encrypted `-secrets.yaml` twins |
| `deploy-as-code/helm/charts/kargo/config/projects/` | Kargo project configs; also read by the Kargo-managed ApplicationSets |
| `deploy-as-code/helm/.sops.yaml` | Which key encrypts which secrets file |

### The bootstrap app

Each cluster runs one hand-applied Application (for example `unified-dev-bootstrap`) that syncs the `argo-cd/<env>/` folder **recursively** (`*.yaml`). Adding a file under that folder creates the object; there is no list to update.

- It has `selfHeal: true`: edits made on the cluster to those objects are reverted.
- It has `prune: false`: **deleting a file does not delete the object.** Old AppProjects or ApplicationSets must be removed by hand after their files are removed (see 2.9).

### AppProject: the security boundary

Every area has an AppProject. It decides:

- **`sourceRepos`**: every repository an Application may use, **including Helm repositories**.
- **`destinations`**: the namespaces Applications may deploy into. An object rendered into any other namespace fails the whole sync instead of touching another module.
- **`clusterResourceWhitelist`**: cluster-scoped kinds allowed. Keep it empty unless a chart truly needs one.

Example, `argo-cd/unified-dev/digit3-core/digit3-core-app-project.yaml`:

```yaml
spec:
  sourceRepos:
    - https://github.com/egovernments/DIGIT-DevOps.git      # values
    - https://helm.digit.org/digit3/core                    # service charts
    - https://helm.digit.org/digit3/cluster-configs         # module ConfigMaps/Secrets
  destinations:
    - namespace: 'digit3-core'
      server: https://kubernetes.default.svc
    - namespace: 'vault'
      server: https://kubernetes.default.svc
```

## 2.3 From env file to running Deployment

What happens after a promotion (or a PR) changes `<service>.chart-version` or `<service>.image.tag`:

1. **Commit lands** on the env branch, for example `kargo: promote mdms-v2 to dev`.
2. **The ApplicationSet re-reads the env file.** Its git generator polls every 60 seconds (`requeueAfterSeconds: 60`).
3. **The Application is regenerated:**
   - `source.chart` = the service's chart name;
   - `source.targetRevision` = `<service>.chart-version`;
   - `helm.valuesObject` = the service's values from the env file (see 2.5), including `image.tag`.
4. **Argo CD renders** the chart at that version with those values and **compares** the result with the cluster.
5. **Automated sync applies** the differences (server-side apply). The Deployment's pod template changes, so Kubernetes rolls out new pods; any migration init container runs first.
6. **Health** follows the rollout: Progressing until the new pods are Ready, then Healthy.

Typical time from the commit to the sync starting: about one minute.

Two details decide what actually runs:

- **The chart version is exact.** A version deleted from the Helm repository can no longer be rendered. Argo CD shows `ComparisonError` and keeps the last applied state.
- **Some charts ignore `image.tag` unless told otherwise.** The DIGIT 3.0 common chart uses the chart's `appVersion` in `prod` mode and honours `image.tag` only in `dev` mode, so environments where Kargo promotes image tags set:

  ```yaml
  global:
    mode: dev     # use the promoted image.tag, not the chart's appVersion
  ```

## 2.4 Two ways to define the Applications

### A. Kargo-managed: declare once in the Kargo config (recommended with Kargo)

A small set of **shared ApplicationSets** (`argo-cd/<env>/kargo-managed/`) read every Kargo project config that has an `argocd:` block, then that project's env file. They create one Application per service **once its `chart-version` exists in the env file**, which is after its first promotion. Adding a service is one entry in the Kargo config; no ApplicationSet changes.

```yaml
# charts/kargo/config/projects/digit-core3-0.yaml
kargo:
  argocdAppPrefix: digit3-
  argocd:
    project: digit3-core-project        # AppProject the Applications use
    namespace: digit3-core              # default namespace
    namespaces: [digit3-core, vault]    # must equal the AppProject's destinations
    layout: common                      # default values layout (2.5)
  services:
    - name: mdms-v2                     # → Application digit3-mdms-v2 in digit3-core
      chart: mdms-v2
    - name: vault
      chart: vault
      image: false
      deploy:                           # only where it differs from the defaults
        layout: root
        namespace: vault
```

| Application field | Taken from |
|---|---|
| name | `deploy.app`, else `argocdAppPrefix` + service name |
| AppProject | `kargo.argocd.project` |
| namespace | `deploy.namespace`, else `kargo.argocd.namespace` |
| chart, Helm repo | `chart`, `chartRepo` (service, else project) |
| chart version | `<valuesKey>.chart-version` in the stage's env file |
| release name | `deploy.releaseName`, else the service name |

The Kargo chart refuses to render a project whose service names an unknown layout, or a namespace outside `kargo.argocd.namespaces`.

### B. Argo CD only: a hand-listed ApplicationSet

Without Kargo, keep the same packaged-chart model but list the services yourself. **People write the chart version and image tag in the env file by PR.**

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: <env>-<module>-appset
  namespace: argocd
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]
  generators:
    - matrix:
        generators:
          - list:
              elements:
                - name: localization        # one element per service
                - name: filestore
          - git:
              repoURL: https://github.com/<org>/<repo>.git
              revision: <env-branch>
              files:
                - path: deploy-as-code/helm/environments/<module>-<env>.yaml
              requeueAfterSeconds: 60
  template:
    metadata:
      name: '<prefix>{{ .name }}'
    spec:
      project: <module>-project
      source:
        repoURL: https://<helm-repo>
        chart: '{{ .name }}'
        targetRevision: '{{ index . .name "chart-version" }}'
        helm:
          releaseName: '{{ .name }}'
      destination:
        server: https://kubernetes.default.svc
        namespace: <namespace>
      syncPolicy:
        automated: { prune: false, selfHeal: true }
        syncOptions: [ApplyOutOfSyncOnly=true, ServerSideApply=true]
  templatePatch: |
    spec:
      source:
        helm:
          valuesObject:
            global: {{ toJson .global }}
            {{ .name }}: {{ toJson (index . .name) }}
```

With `missingkey=error`, a listed service whose env file has no `chart-version` stops the whole ApplicationSet from generating. Add the element only once the version is in the env file, or guard the generator with a selector (`matchExpressions: [{key: <service>.chart-version, operator: Exists}]`).

| | A. Kargo-managed | B. Argo CD only |
|---|---|---|
| Who writes `chart-version` / `image.tag` | Kargo promotion | People, by PR |
| Add a service | One entry in the Kargo config | One list element + values in the env file |
| ApplicationSet edits per service | None | One |
| Promotion between environments | Kargo, gated | A PR per env branch |

## 2.5 How values reach a chart (layouts)

Charts expect their values in different shapes. A **layout** is how an Application hands the env file's values to its chart. Each layout is one ApplicationSet; services choose a layout, not an ApplicationSet.

| Layout | Values given to the chart | Use for |
|---|---|---|
| `common` | `{ global: <env global>, <service>: <env service section> }` | Charts built on a shared library chart that reads `.Values.global` and `.Values.<service>` (the DIGIT service charts) |
| `root` | The service's section **as the root values**, minus `chart-version`; CRDs skipped | Third-party-style charts that read plain root values (Kong, Vault) |
| `configs` | The whole env file plus its `-secrets.yaml` twin, as value files from git | The module's ConfigMaps/Secrets chart (cluster-configs) |

Namespace is independent of layout: two services in the same layout can deploy to different namespaces. A new ApplicationSet is needed only for a chart that takes values in a way none of the layouts provide; it then serves every project.

**Env-file sections are keyed by chart name.** The `common` layout passes `<service>` as the key, and the library chart merges `.Values.<chart-name>` over the chart's defaults. A section under any other name is silently ignored.

## 2.6 Configuration and secrets

### Module ConfigMaps and Secrets

Each module gets its own config Application, which renders the module's ConfigMaps (for example `egov-config`, `egov-service-host`) and Secrets, **only into the module's namespaces**:

- **Kargo-managed:** the service with `deploy.layout: configs` (for example the `cluster-configs` service of `digit-core3-0`, app `digit3-core-cluster-configs`).
- **Standalone:** a dedicated Application using the cluster-configs chart with `values.yaml`, the module env file and its secrets file (for example `digit-lts-cluster-configs-studio`).

Never layer a module's env file onto another module's config Application: a ConfigMap with the same name would replace the other module's.

### Secrets

- Secret values live in `environments/<module>-<env>-secrets.yaml`, **encrypted with SOPS**. The key is chosen by a rule in `deploy-as-code/helm/.sops.yaml` (Azure Key Vault or AWS KMS). The rule must exist **before** the file is created.
- Argo CD's repo-server decrypts the file at render time. Single-source Applications reference it as `secrets://../../environments/<file>`; the multi-source `configs` layout reads it through the `$values` source.
- Edit with `sops <file>`, never with a plain editor. Never commit decrypted values.

### Where a value should live

| Value | Put it in |
|---|---|
| Shared by every service in the module (DB host, Kafka brokers, domain) | `cluster-configs.configmaps.egov-config.data` in the module env file |
| Another service's address | `cluster-configs.configmaps.egov-service-host.data` |
| A password, key or token | The module's `-secrets.yaml`, via SOPS |
| One service's setting (replicas, ingress, an env override) | That service's section in the env file |
| Chart version, image tag | Written by Kargo (or by PR in Argo CD only mode) |

## 2.7 Onboard a new application

### With Kargo (layout A)

1. Publish the chart; make sure matching image tags exist.
2. Add the service to the Kargo project config. Add `deploy:` only if its layout or namespace differs from the project defaults.
3. Add its hand-written values to the env file(s), keyed by the chart name.
4. If it needs another namespace, add it to the AppProject's `destinations` **and** to `kargo.argocd.namespaces` in the same PR.
5. Merge, assemble Freight, promote to dev. The Application `<prefix><service>` appears within about a minute; check it syncs and becomes Healthy.

### Argo CD only (layout B)

1. Publish the chart.
2. In the env file, add the service's section with `chart-version`, `image.tag` (and the migration tag if any) and its values.
3. Add one element to the module's ApplicationSet (or use the selector from 2.4).
4. Namespace changes as above (AppProject `destinations`).
5. Merge; check the Application syncs and becomes Healthy. Later version changes are PRs that edit `chart-version` / `image.tag`.

### Before raising either PR

- Render the chart with the env file (`helm template`), and look for duplicate env var names (2.10).
- Check every ConfigMap/Secret key the chart references exists in the target namespace.
- Check the Ingress path is not already used on the same host.

## 2.8 Onboard a new module

1. **Env files** per environment: `global` (namespace, domain, mode), the `cluster-configs` section (namespaces, ConfigMaps, Secret declarations), service sections.
2. **Secrets**: the `.sops.yaml` rule, then the `-secrets.yaml` file created and edited with `sops`.
3. **AppProject** in `argo-cd/<env>/<module>/<module>-app-project.yaml`: `sourceRepos` (git + Helm repos), `destinations`, no cluster-scoped kinds unless needed.
4. **Applications**:
   - with Kargo: the project config's `argocd` block (layout A), plus the Kargo onboarding steps in the Kargo doc;
   - without Kargo: the module's ApplicationSet (layout B) and a config Application.
5. **Namespace**: created by the config Application (`cluster-configs.namespaces`), or by the cluster-wide config if it already lists the namespace. **Exactly one Application may own a Namespace object.**
6. **Order on first sync**: the AppProject must exist before an ApplicationSet that uses it is first reconciled. If an ApplicationSet reports "application references project … which does not exist", refresh it once the AppProject exists (2.10).

## 2.9 How deployments are handled

Standard sync policy for generated Applications:

```yaml
syncPolicy:
  automated:
    prune: false        # removed resources are not deleted automatically
    selfHeal: true      # cluster drift is reverted to git
  syncOptions:
    - ApplyOutOfSyncOnly=true
    - ServerSideApply=true
  retry:
    limit: 10
    backoff: { duration: 5s, factor: 2, maxDuration: 3m0s }
ignoreDifferences:
  - group: apps
    kind: Deployment
    jsonPointers: [/spec/replicas]   # replicas may be scaled outside git
```

What this means day to day:

- **Edits on the cluster do not stick.** A `kubectl edit` of a managed object is reverted within seconds. Change git instead.
- **Removals need a person.** With `prune: false`, a resource that disappears from the render stays on the cluster until removed by hand.
- **Ownership.** An Application belongs to the ApplicationSet that created it. Another ApplicationSet cannot take it over and reports "already owned by another ApplicationSet". To move an Application between ApplicationSets, delete the old ApplicationSet with `kubectl delete applicationset <name> --cascade=orphan`: the Applications and workloads stay, and the new ApplicationSet adopts them by name.
- **Deleting an ApplicationSet** without `--cascade=orphan` deletes its Applications. Their workloads stay only if the Applications have no deletion finalizer.
- **Rollback** is a git revert, or (with Kargo) promoting the previous Freight.

## 2.10 Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Sync fails: `duplicate entries for key [name="X"]` | The chart renders the same env var twice; server-side apply rejects the Deployment | Remove the duplicate in the chart, or have the library chart merge env by name (last wins) |
| `one or more synchronization tasks are not valid`, CRDs listed | The chart ships `crds/`; Argo CD installs them unless told not to | `helm.skipCrds: true` (the `root` layout sets it) |
| `namespace X is not permitted in project` | Rendered object outside the AppProject's destinations | Fix the chart's namespace, or add the namespace to the AppProject deliberately |
| ApplicationSet: `references project … which does not exist` | ApplicationSet reconciled before its AppProject existed | Refresh the ApplicationSet (annotation `argocd.argoproj.io/application-set-refresh: "true"`) |
| ApplicationSet: `already owned by another ApplicationSet` | Two ApplicationSets generate the same Application name | Orphan-delete the old ApplicationSet (2.9) |
| Application missing after a promotion | Layout A: no `chart-version` yet, or a service/layout mismatch. Layout B: service not listed | Check the env file commit and the generator |
| `ComparisonError` / chart not found | The pinned chart version was removed from the Helm repo | Promote or pin a published version; never delete versions in use |
| Pod `CreateContainerConfigError: couldn't find key …` | A ConfigMap/Secret key the chart reads is missing in that namespace | Add the key to the module's config (env file or secrets) |
| Pod `ErrImagePull` with an unexpected tag | The chart ignored `image.tag` (prod mode) or the tag does not exist | Set the chart's mode switch; check the tag exists for app and `-db` images |
| Change reverted seconds after `kubectl edit` | `selfHeal` | Change git |
