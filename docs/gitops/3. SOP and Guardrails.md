# 3. SOP and Guardrails

The operating procedure for every change made through Kargo, Argo CD, or both together. Each rule has a reason; when a situation is not covered, apply the principles in 3.1 and stop for review rather than improvising.

Terms follow [1. Kargo: Setup and Onboarding](1.%20Kargo%20-%20Setup%20and%20Onboarding.md) and [2. Argo CD: Setup and Onboarding](2.%20Argo%20CD%20-%20Setup%20and%20Onboarding.md). **MUST** / **MUST NOT** are mandatory; **SHOULD** is the default, departing from it needs a stated reason in the PR.

## 3.1 Principles

1. **Git is the source of truth.** The desired state of every environment is what is on its branch. Anything else is drift, and will be reverted or lost.
2. **Every change is a reviewed PR.** No direct commits to environment branches. The only automated writer is a Kargo promotion, and only for the keys it owns.
3. **One owner per thing.** Each env-file key, each Kubernetes object and each Application has exactly one writer. Two writers fight.
4. **Smallest scope that works.** Change one service rather than a shared file; override per application rather than changing a shared default.
5. **Prove before merge, verify after.** Render and compare before the PR; check sync, health and logs after the merge.
6. **No hidden side effects.** A change that alters anything beyond its stated purpose must show that impact in the PR, or be split.
7. **Secrets are never visible.** Not in git (in plaintext), not in logs, not in PR text, not in chat.
8. **Stop on surprise.** An unexpected diff, error or permission problem stops the change until it is understood. Do not work around it.

## 3.2 Who writes what

| Item | Written by | Everyone else |
|---|---|---|
| `<service>.chart-version`, `<service>.image.tag`, `<service>.initContainers.dbMigration.image.tag` in an env file | **Kargo** (promotion) | Do not edit, except in Argo CD only mode (3.15) or a recorded emergency (3.14) |
| All other env-file values (global, replicas, ingress, ConfigMap data) | People, by PR | — |
| Secrets files | People, with `sops`, by PR | — |
| Kargo project config, ApplicationSets, AppProjects | People, by PR | — |
| Kubernetes objects of managed Applications | **Argo CD** | Do not edit on the cluster (selfHeal reverts) |
| Freight | Members of the team allowed to assemble Freight | — |
| Promotions | Promoters for that stage | — |

## 3.3 Repository and branches

- **MUST** change environments only through PRs to their branch (`unified-dev`, `unified-qa`, `unified-uat`, or the cluster's own branch).
- **MUST** branch from the latest remote base, and keep one purpose per PR.
- **MUST NOT** force-push or rewrite environment branches. Kargo pushes promotion commits to them; rewriting loses promotions.
- **MUST** check after a merge that the merged commit contains every intended commit. A PR merged while a later push was still registering may leave it out; raise the missing commit again rather than assuming it landed.
- **SHOULD** keep a module's values in its own env file (`<prefix>-<module>-<env>.yaml`), never in another module's, so keys cannot collide.

## 3.4 Kargo guardrails

**Warehouses and tags**

- **MUST** anchor tag filters on the trailing commit hash (`…[0-9a-f]{7,}$`) so per-architecture children (`-amd64`, `-arm64`) never become Freight.
- **MUST** widen the filter for one service with `extraAllowTags`, never by loosening the project-wide `allowTags`.
- **MUST NOT** create, edit or delete Warehouses, Stages or Projects by hand; change the project config.
- **SHOULD** keep `freightCreationPolicy: Manual`.

**Freight**

- **MUST** choose the image tag and chart version explicitly when assembling Freight; do not rely on list order.
- **MUST** confirm that the app image and, if the service migrates a database, its `-db` image both exist for the chosen tag.
- **MUST** confirm that the chart version is published and will stay published.

**Promotion**

- **MUST** promote in order: dev → qa → uat. Keep `autoPromotion: false`.
- **MUST** promote only `master-*` builds to uat. **MUST NOT** add exemptions to the master-only rule, for any service.
- **MUST** promote one service at a time and check it (3.11) before the next, unless a release plan says otherwise.
- **MUST** use `envFileWrite: merge` for new projects.
- **MUST NOT** hand-edit a key Kargo owns to "speed up" a promotion.

**Projects and access**

- **MUST** give each project a unique `argocdAppPrefix`.
- **MUST** grant access through the project's `teams:` list only; grant Freight assembly (`manageFreight`) only to the team that assembles it.

## 3.5 Argo CD guardrails

**AppProjects**

- **MUST** list every source repository an Application uses, including Helm repositories, in `sourceRepos`.
- **MUST** list destinations explicitly. **MUST NOT** use `namespace: '*'` for application projects.
- **MUST** keep `clusterResourceWhitelist` empty unless a chart requires a cluster-scoped kind; name the kind and the reason in a comment.
- **MUST** add a new namespace to the AppProject in the same PR as the first Application that deploys there (and to `kargo.argocd.namespaces` for Kargo-managed projects).

**ApplicationSets and Applications**

- **MUST** keep exactly one ApplicationSet generating each Application name.
- **MUST** move an Application between ApplicationSets only by:
  1. merging the new ApplicationSet;
  2. deleting the old one with `--cascade=orphan`;
  3. confirming that the new one adopted the Application.
- **MUST** remember that removing a manifest file does not remove the object (`prune: false` on the bootstrap app); plan the manual cleanup in the PR description.
- **MUST** use the standard sync policy (Argo CD doc, 2.9) for generated Applications. **MUST NOT** enable `prune` without a review of what it would delete.
- **MUST** set `helm.skipCrds: true` for charts that ship CRDs, when the AppProject allows no cluster-scoped kinds.
- **SHOULD** choose an existing layout (`common`, `root`, `configs`). Add a new layout ApplicationSet only for a chart none of them can serve.
- **SHOULD NOT** hard-refresh an Application without need. A hard refresh drops the cached render, and an Application pinned to a deleted chart version then fails to render.

**Shared configuration**

- **MUST NOT** change a shared object (a namespace's `egov-config` / `egov-service-host`, a library chart, the cluster-wide config chart) without listing every consumer and its effect in the PR.
- **SHOULD** solve one application's problem with an override in that application's values (for example a chart value selecting a different ConfigMap key), not by changing the shared object.
- **MUST**, when changing a library chart or a shared template, render the unaffected applications before and after and show they are byte-identical.

## 3.6 Charts and values

- **MUST** key a service's env-file section by its chart name; other keys are silently ignored.
- **MUST** restate a whole list when overriding one in an env file. Helm replaces lists, it does not merge them, so a dropped item is removed (and `selfHeal` enforces it).
- **MUST** check rendered Deployments for duplicate env var names before merge. Server-side apply rejects the whole Deployment. Fix it in the chart, or rely on a library chart that merges env by name.
- **MUST** check which image tag a chart actually uses. Some charts ignore `image.tag` unless a mode switch is set (DIGIT 3.0 common chart: `global.mode: dev`).
- **MUST** keep hostnames out of charts; take them from the module's `egov-service-host` / `egov-config`.
- **MUST NOT** delete a published chart version that any environment pins.
- **MUST** emit one YAML document per object in templates that loop over namespaces (`---` inside the loop). A single separator before the loop puts every object in one document, and only the last one is applied.

## 3.7 Databases and migrations

- **MUST** give each module's tables their own schema when modules share a database. Point the module's services at a schema-scoped URL (for example `studio-db-url` with `currentSchema=studio`) rather than the shared default.
- **MUST** run an app image and its migration (`-db`) image from the same build tag. Mixing builds corrupts the migration history (checksum mismatches).
- **MUST NOT** run `flyway repair`, drop tables, or edit a schema-history table without explicit approval and a written reason. Prefer fixing the configuration (schema, image) over repairing history.
- **MUST**, for data copies between environments:
  1. read the source only;
  2. stream the data without saving it locally;
  3. load it in a single transaction that rolls back if any row is skipped;
  4. dry-run first (rolled back);
  5. verify with row counts and hashes on both sides.
- **MUST NOT** grant a superuser login as "read access". Create a role with only the privileges needed (for example `pg_read_all_data`).

## 3.8 Secrets and access

- **MUST** create the `.sops.yaml` rule before creating a secrets file, and edit secrets only with `sops`.
- **MUST NOT** commit decrypted values, paste them into PRs or messages, or print them in terminal output. To share a credential, use a password manager or another secure channel.
- **MUST NOT** copy one environment's cluster credentials (API URLs, tokens) into another environment's secrets. Create credentials for the target cluster.
- **MUST** grant cluster access with the least privilege that does the job. For a debugging/read role: view workloads, logs, configmaps, services and ingresses; exec, port-forward and pod delete if needed; **never Secrets**. Prefer namespaced access where possible.
- **MUST** record every access grant (manifest path, who it is for, how to revoke) in the PR or change record, even when it is applied outside git.
- **MUST** keep any local file holding a credential readable only by its owner (`chmod 600`), and delete it once the credential is stored in its proper place.

## 3.9 Changes outside git

Some actions cannot be expressed as a PR: creating a database role, a one-off token, deleting an orphaned ApplicationSet, a data copy.

- **MUST** be the exception, with a stated reason.
- **MUST** be reviewed (server-side dry run, or the exact command shown) before running.
- **MUST** be recorded in a PR description or change record: what was run, where, and how to undo it.
- **MUST NOT** be used to change something Argo CD manages. `selfHeal` reverts it within seconds; change git instead.
- **SHOULD** use read-only checks freely (listing objects, `kubectl auth can-i`, rendering, read-only queries); they need no approval.

## 3.10 Before raising a PR

Run the checks that apply; paste the results (not secrets) in the PR.

- [ ] **Render the changed chart** with the real env file:
  ```sh
  helm template <svc> <chart> --version <v> -n <ns> -f <values>
  ```
- [ ] **Compare before and after** for anything shared. Unrelated applications must be byte-identical.
- [ ] **No duplicate env var names** in rendered Deployments.
- [ ] **Every referenced ConfigMap/Secret key exists** in the target namespace (or is added in the same PR).
- [ ] **Every image tag** (app and `-db`) and **chart version exists** in its registry or repository.
- [ ] **Ingress paths do not clash** with existing paths on the same host.
- [ ] **New namespace** is in the AppProject destinations (and in `kargo.argocd.namespaces`).
- [ ] **Kargo project config renders** (`helm template` of the Kargo chart with the project file); unrelated projects are byte-identical.
- [ ] **Argo CD manifests pass a server-side dry run:**
  ```sh
  kubectl apply --dry-run=server -f <file>
  ```
- [ ] **Secrets** files are encrypted (`grep -c 'ENC\['` > 0) and match the `.sops.yaml` rule.
- [ ] **The PR description** states purpose, effect, verification and any manual follow-up (orphan deletes, out-of-git steps).

## 3.11 After merge

- [ ] **The merged commit contains every commit** from the PR (3.3).
- [ ] **The bootstrap app / ApplicationSet is on the merge revision.** A normal refresh is fine; avoid hard refresh (3.5).
- [ ] **Each affected Application is `Synced`.** For any `OutOfSync`, read the sync result before acting.
- [ ] **Each affected Application becomes `Healthy`.** For `Progressing` or `Degraded`, check the pods (init containers first), then the container logs.
- [ ] **For a promotion:** the Deployment runs the promoted image tag and the chart version matches.
- [ ] **Record what is still broken and who owns it.** Do not leave a failure unexplained.

## 3.12 Approval levels

| Change | Approval |
|---|---|
| Promote Freight to dev | Dev promoter |
| Promote to qa / uat | Promoter for that stage; uat only `master-*` |
| Add a service to an existing project/module, values for one service | One reviewer |
| New project or module, new AppProject or namespace, new layout ApplicationSet | Platform owner review |
| Change to shared config, library chart, cluster-wide config chart, sync policy | Platform owner review with a before/after render diff |
| Access grants, database roles, data copies, orphan deletes, anything outside git | Explicit approval from the environment owner, recorded |
| Schema-history repair, dropping data | Explicit approval from the service owner and the environment owner |

## 3.13 Never do

- Commit directly to, force-push or rewrite an environment branch.
- Edit Kargo-owned keys by hand (outside 3.14/3.15).
- Allow non-`master-*` builds into uat, or add exemptions.
- Create or edit Kargo objects, or Argo CD-managed objects, directly on a cluster.
- Let two ApplicationSets generate the same Application, or delete an ApplicationSet without `--cascade=orphan` when its Applications must stay.
- Use `namespace: '*'` or broad cluster-scoped kinds in an application AppProject.
- Delete a published chart version that is in use.
- Commit, print or paste decrypted secrets, or reuse one cluster's credentials in another.
- Give superuser database access as "read" access, or grant Secret read in a debugging role.
- Repair migration history or drop data without approval.

## 3.14 Recovery procedures

| Situation | Do this |
|---|---|
| Bad promotion (app broken after a version change) | Promote the previous Freight to that stage. If Kargo is unavailable, revert the promotion commit by PR, and note it so the next promotion is not confused. |
| Bad configuration PR | Revert the PR. |
| Application stuck `OutOfSync` with a sync error | Read the sync result (duplicate env, namespace not permitted, CRDs, missing project); fix in git. Do not edit the cluster. |
| ApplicationSet errors after its AppProject was created | Refresh the ApplicationSet once the AppProject exists. |
| "Already owned by another ApplicationSet" | Orphan-delete the old ApplicationSet (after approval), then confirm adoption. |
| Old pod stuck while a rollout cannot complete | Fix the new pod; the old ReplicaSet scales down once the new pods are Ready. Do not delete it to "unblock". |
| Migration checksum mismatch after mixing builds | Stop. Compare the migration files of both builds, then decide with the service owner between running matching builds and an approved repair. |
| Secret exposed | Rotate it at the source, update the encrypted file by PR, and record the incident. |

## 3.15 Argo CD only mode

Without Kargo, the same rules apply with these differences:

- **People write** `chart-version`, `image.tag` and the migration tag in the env file, by PR, one environment branch at a time.
- **Promotion between environments** is a PR to the next branch with the same versions. Promote in order dev → qa → uat, and only `master-*` builds to uat.
- **Applications come from the module's hand-listed ApplicationSet** (Argo CD doc, layout B). Add the list element only when the env file has the version, or guard the generator with a selector on `<service>.chart-version`.
- **Everything in 3.5 to 3.13 applies unchanged.**
