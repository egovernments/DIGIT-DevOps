# 2. Setup

How the Kargo control plane, its supporting applications and all credentials are set
up on the unified-dev cluster. This is already deployed; this page explains what is in
place and how to reproduce it. See [Overview](1.%20Overview.md) for the model.

Everything is GitOps. The app of apps (`unified-dev-bootstrap`) applies the ArgoCD
manifests under
[argo-cd/unified-dev/kargo](../../deploy-as-code/helm/charts/argo-cd/unified-dev/kargo),
and those applications bring up the rest.

## 2.1 ArgoCD applications

| File | Kind | Purpose |
|------|------|---------|
| [kargo-app-project.yaml](../../deploy-as-code/helm/charts/argo-cd/unified-dev/kargo/kargo-app-project.yaml) | AppProject | `kargo-project`: the source repos, namespaces and cluster scoped kinds the Kargo apps may use |
| [kargo-application.yaml](../../deploy-as-code/helm/charts/argo-cd/unified-dev/kargo/kargo-application.yaml) | Application | The control plane: upstream chart from `ghcr.io/akuity/kargo-charts`, values from `config/control-plane.yaml` |
| [argo-rollouts-application.yaml](../../deploy-as-code/helm/charts/argo-cd/unified-dev/kargo/argo-rollouts-application.yaml) | Application | Argo Rollouts, required for verification |
| [kargo-app-set-pipelines.yaml](../../deploy-as-code/helm/charts/argo-cd/unified-dev/kargo/kargo-app-set-pipelines.yaml) | ApplicationSet | One `kargo-<project>` Application per project |

## 2.2 Control plane

The control plane is the upstream Kargo chart, pinned to `1.11.4`, installed as a
multi source Application: the chart comes from the OCI registry and the values come
from this git repo through the `$values` ref. All non secret settings are in
[control-plane.yaml](../../deploy-as-code/helm/charts/kargo/config/control-plane.yaml).

Key settings and why:

- **Ingress** at `kargo.digit.org`, class `nginx`, TLS issued by cert-manager
  (`letsencrypt-prod`). The API serves plain HTTP behind nginx
  (`api.tls.enabled: false`) but `api.tls.terminatedUpstream: true` forces the
  generated URLs to https, so UI assets are not blocked as mixed content.
- **Admin account** stays enabled with its password hash and token signing key
  supplied from the `kargo-api` Secret (`api.secret.name`), not inline. See 2.5.
- **GitHub SSO** through the bundled Dex. See
  [Role Based Promotion Access](4.%20Role%20Based%20Promotion%20Access.md).
- **ArgoCD integration** points at the in cluster ArgoCD (`controller.argocd`) so the
  DEV `argocd-update` step works.
- **Two webhook replicas** (`webhooksServer.replicas: 2`) so bulk applies (for
  example onboarding many warehouses at once) do not time out the admission webhook.

## 2.3 Argo Rollouts

Verification uses Argo Rollouts' `AnalysisTemplate` and `AnalysisRun` CRDs and its
controller to run the check Jobs. It is installed from the argoproj Helm repo by
[argo-rollouts-application.yaml](../../deploy-as-code/helm/charts/argo-cd/unified-dev/kargo/argo-rollouts-application.yaml).
The Kargo controller detects the CRDs at startup; if Rollouts is installed after
Kargo, restart the Kargo controller once so it enables the integration.

## 2.4 Prerequisites

- DNS for `kargo.digit.org` pointing at the nginx ingress load balancer IP of the
  unified-dev cluster, so cert-manager can issue the certificate.
- The SOPS encrypted secrets populated as below.
- A GitHub OAuth app for Dex and a GitHub App for git push.

## 2.5 Secrets and credentials

None of the credentials are created by hand in the cluster. They are declared in git
and rendered by the cluster-configs template
[kargo-secret.yaml](../../deploy-as-code/helm/charts/cluster-configs/templates/secrets/kargo-secret.yaml),
which the `cluster-configs-unified-dev` application applies.

### Where values live

- **Non secret metadata** (which projects, Secret names, namespaces, enabled flags)
  is in
  [cluster-configs values.yaml](../../deploy-as-code/helm/charts/cluster-configs/values.yaml)
  under `cluster-configs.secrets.kargo`.
- **Secret values** are SOPS encrypted in
  [unified-dev-secrets.yaml](../../deploy-as-code/helm/environments/unified-dev-secrets.yaml)
  under the same `cluster-configs.secrets.kargo` key.

The template deep merges the two.

### What gets rendered

| Rendered Secret | Namespace | From | Used for |
|-----------------|-----------|------|----------|
| `image-creds-0` (label `kargo.akuity.io/cred-type: image`) | each project ns | `imageCredentials` | Pulling image tags during discovery |
| `git-creds-0` (label `kargo.akuity.io/cred-type: git`) | each project ns | `gitCredentials` | Pushing the promotion commit |
| `kargo-api` | `kargo` | `adminSecret` | Admin password hash and token signing key |
| `kargo-dex-github` | `kargo` | `dexSecret` | GitHub OAuth app for SSO |
| `verify-kubeconfig-<env>` | each project ns | `verifyKubeconfigs` | Read only kubeconfig the verification Job uses |

The image, git and verification Secrets render into every namespace in the `projects`
list, so each project picks them up.

### Editing the secrets

The file is encrypted with SOPS against AWS KMS. Edit with the egov profile:

```
AWS_PROFILE=egov sops deploy-as-code/helm/environments/unified-dev-secrets.yaml
```

Shape under `cluster-configs.secrets.kargo`:

```yaml
cluster-configs:
  secrets:
    kargo:
      imageCredentials:
        - repoURL: '^docker\.io/egovio/.*'
          repoURLIsRegex: "true"
          username: <docker user>
          password: <docker token>
      gitCredentials:
        - repoURL: https://github.com/egovernments/DIGIT-DevOps.git
          githubAppID: "<app id>"
          githubAppInstallationID: "<installation id>"
          githubAppPrivateKey: |
            -----BEGIN RSA PRIVATE KEY-----
            ...
      adminSecret:
        passwordHash: <bcrypt hash>
        tokenSigningKey: <random string>
      dexSecret:
        clientID: <github oauth client id>
        clientSecret: <github oauth client secret>
      verifyKubeconfigs:
        dev: |
          apiVersion: v1
          kind: Config
          ...
        qa: |
          ...
        uat: |
          ...
```

Saving re encrypts in place. Prefer `sops set ... --value-stdin` for a single field,
which preserves the existing key recipients.

### The individual credentials

- **Image pull:** a Docker account whose pull rate limit is high enough for
  discovery. Confirm with a live check that Docker Hub reports a higher or absent
  `ratelimit-limit` for that login, not the free `200;w=3600`. `repoURL` is a regex
  (`repoURLIsRegex: "true"`) so one entry covers every `docker.io/egovio/*` repo.
- **Git push:** a GitHub App with Contents read and write. Supply `githubAppID`,
  `githubAppInstallationID` and the PEM `githubAppPrivateKey`; the repo URL must be
  https. The environment branches (`unified-dev`, `unified-qa`, `unified-uat`) are
  protected, so the App must be allowed to push to them (bypass the pull request
  requirement, or switch the promotion to open a PR).
- **Admin account:** generate the two values with:
  ```
  htpasswd -bnBC 10 '' 'YOUR_ADMIN_PASSWORD' | tr -d ':\n' | sed 's/$2y/$2a/'   # passwordHash
  openssl rand -base64 48 | tr -d '=+/' | cut -c1-32                            # tokenSigningKey
  ```
  The `enabled`, `name` and `namespace` metadata live in cluster-configs values.
- **GitHub SSO (Dex):** `clientID` and `clientSecret` from a dedicated GitHub OAuth
  App (callback `https://kargo.digit.org/dex/callback`); set `dexSecret.enabled: true`
  in cluster-configs values.
- **Verification kubeconfigs:** one read only kubeconfig per environment cluster,
  keyed `dev`, `qa`, `uat`, each a service account token scoped to read Deployments in
  the target namespaces.

### Rotating

Edit the field with `sops`, commit, merge. The cluster-configs application re renders
the Secret. Workloads that mount it (the Kargo API for `kargo-api`, Dex for
`kargo-dex-github`) may need a restart to pick up the new value.
