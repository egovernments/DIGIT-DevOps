# Kargo Build and Promotion SOP

Standard operating procedure for teams who build services and promote them through the
unified environments (DEV, then QA, then UAT) using Kargo. Everything is done in the
Kargo UI after signing in with GitHub; you never touch git or kubectl for a promotion.

Kargo UI: **https://kargo.digit.org**

---

## 1. Sign in (GitHub SSO)

1. Open https://kargo.digit.org and choose **Log in with GitHub**.
2. Authorise the app once. There is no separate Kargo password.
3. What you can see and do is decided by your **GitHub team membership**. You only see the
   projects your team is granted, and you can only promote into the stages your team is
   allowed to.

If a project is missing, or a **Promote** button is greyed out or absent, you are not in
the team that grants that access. Request it from the platform/DevOps owner (do not share
logins).

### Roles at a glance

| Role | What it allows |
|------|----------------|
| Viewer | See the project, its stages and freight. Promote nothing. |
| Promoter (per stage) | Promote into the specific stage(s) your team is granted (for example DEV only, or QA only, or UAT only). |
| Admin | Manage the project (platform team only). |

Promotion rights are **per stage**. A DEV promoter cannot promote to QA or UAT, and so on.
Access control detail lives in `docs/kargo/4. Role Based Promotion Access.md`.

---

## 2. Build tag syntax (read this before you build)

Kargo only promotes images whose **tag** matches the rules below. A build tagged the wrong
way will simply never appear in Kargo. There is one image warehouse per service.

### The rules

1. **Every tag must end in the git commit short SHA** (hex, 7+ characters): `...-<sha>`,
   for example `...-1e8d2bb`. This is mandatory. The per-architecture children
   (`-amd64`, `-arm64`) are deliberately excluded because they do not end in a hex SHA.
2. **Mainline builds:** `master-<sha>`, for example `master-1e8d2bb`.
   **Only `master-*` tags can reach UAT.**
3. **Feature / ticket builds** (allowed into DEV and QA, never UAT) follow the family
   prefixes, as `PREFIX-<ticket>-<slug>-<sha>`:

   | Prefix families (health project) |
   |----------------------------------|
   | `FEATURE`, `BUGFIX`, `RELEASE`, `HCMPRE`, `DPG`, `SN`, `DUCE`, `HCMCONSOLE` |

   Example: `HCMPRE-4356-projectUpdateDate-dbf68c0`.
4. **Service-specific schemes** exist for a few services (for example `boundary-service`
   builds from `master-persister-changes-2.0-<sha>`, and the console/UI services add a
   `newv-*` / `console-*` family). Follow whatever that service already uses.

### Do not

- Do not use `latest`, a bare branch name, or any tag without the trailing SHA. It will
  not be discovered.
- Do not expect a feature/ticket tag to reach UAT. It cannot (see section 4).

### Rule of thumb

If a change must go all the way to UAT, **build it from `master`** so it is tagged
`master-<sha>`. Feature and ticket tags are for DEV and QA testing only.

---

## 3. Promote a build

Promotion is manual and always flows **DEV, then QA, then UAT**. Each stage only offers
freight that was verified in the stage before it, so you cannot skip ahead.

1. Open the Kargo UI and select your **project** (module).
2. Find the service and its **DEV** stage. Click **Promote**.
3. Pick the **Freight** (the image build) you want. Confirm.
4. Watch the stage:
   - It turns **green / Verified** when the tag is running and healthy on that
     environment's cluster. Verification can take up to about 10 minutes (QA and UAT wait
     on their own cluster to pull and roll out).
   - **Red / Failed** means verification did not pass (the roll-out did not complete in
     time, or the pod is unhealthy). See section 5.
5. Once DEV is Verified, repeat for **QA**, then **UAT**.

Promote only through Kargo. Editing an environment's values file directly (a git commit or
PR) bypasses these controls and should not be used for routine promotion.

---

## 4. UAT is master-only

UAT accepts **only `master-*` tags**. If you try to promote any other tag (a feature or
ticket build) to a UAT stage, the promotion **fails (Errored)** with a message like
`REJECTED: only master-* images may be promoted to uat`, and nothing is deployed.

This is expected behaviour, not a bug. To get a change into UAT, build it from `master`
and promote the resulting `master-<sha>` tag.

DEV and QA accept both mainline and feature/ticket builds, so day-to-day testing is
unaffected.

## 5. Troubleshooting

| Symptom | Cause and fix |
|---------|---------------|
| My build does not appear in Kargo | The tag does not match the rules in section 2 (missing SHA suffix, wrong family), or discovery has not run yet. The warehouse re-checks roughly every 30 minutes; use **Refresh** on the warehouse to pull sooner. |
| UAT promotion shows `Errored` / `REJECTED` | The tag is not `master-*`. Rebuild from master (section 4). |
| Stage is **red / verification Failed** | The target cluster did not roll out the tag in time, or the deployment is unhealthy. Wait for the roll-out to finish and use **Reverify**, or check the pod on that cluster. |
| I cannot see my project, or **Promote** is disabled | You are not in the GitHub team that grants that access. Request it from the platform/DevOps owner (section 1). |
| I promoted but the next stage does not offer the freight | The current stage has not finished verifying yet. A downstream stage only offers freight verified in the stage before it. |

---

## 6. Quick reference

- **UI:** https://kargo.digit.org, sign in with GitHub.
- **Order:** DEV, then QA, then UAT. Manual at each step.
- **Tag format:** `master-<sha>` for anything bound for UAT; `PREFIX-<ticket>-<slug>-<sha>`
  for DEV/QA feature builds; always end in the commit SHA.
- **UAT rule:** master-only. Non-master promotions to UAT fail by design.
- **Access:** per-stage, by GitHub team. No project or no Promote button means no access.
- **Do not** edit environment values files directly; promote through Kargo.
